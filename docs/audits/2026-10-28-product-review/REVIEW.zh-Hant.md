# Galeng／Plane 整體產品與工程改善審視

日期：2026-10-28

基準：`work`，`b76f5e20c1f8efb09b27d33959ca3c4cd3a99229`，包含 N1／N2 修正。

目的：審視 BUG 之外的作者工作流程、UI 交互、引擎設計、效能與發布品質。這是改善建議，不是新增功能的實作承諾。

## 判斷

目前最需要投資的，是讓作者能放心持續製作完整遊戲：資料狀態清楚、兩種場景操作一致、預覽與實機的執行規則可驗證、正式版本可重現。單純增加功能面板，會繼續擴大現有的維護與學習成本。

這些建議大部分針對編輯器、host、播放器和格式契約，會服務日後所有使用相關功能的遊戲。Demo 只是重現及驗收素材。播放器改善要隨新版 player 重新匯出／發布才會到達玩家；需要新增格式的功能則要配套版本與遷移規則，不能假定舊遊戲包會自動更新。

不建議全面重寫。JSON IR、共用 schema、原生播放器、兩種專門編輯表面都有保留價值。較合適的方向是共用專案管理與文件生命週期，保留對話時間軸和 Explore 畫布各自擅長的操作。

## 本次方法與限制

- 閱讀 README、`SPEC .txt`、HANDOFF、兩份歷史審查，以及音訊、字體／腳本管理器、Dialogue ↔ Explore 設計交接文件；對照現行程式，沒有把舊文件中的已修項目當成新缺陷。
- 檢視 v2、Explore、共用儲存與歷史機制、host、runtime、Explore engine、存檔、資源／文字、packer、CI／release。
- 用真實 host API 和 Chromium 開啟 `examples/click-room` 的獨立副本；檢視 1440×900、1280×720、1024×768，另操作對話場景及新建場景視窗。
- 這批瀏覽器操作沒有捕捉到未處理的 pageerror；不代表所有流程都沒有錯誤。
- 沒有在 Windows 原生播放器上重新做聲畫、舊硬體或長時間測試，沒有測量大型專案延遲。相關效能項目標為待量測，不宣稱已證實卡頓或符合最低配備。
- 本次沒有重跑全套單元測試；先前測試通過的數字不是本次全面驗收結果。
- 審查時沒有修改專案程式碼、commit 或 push；報告與證據原先保存在倉庫外。其後依使用者要求，將本報告及證據納入此文件目錄發布，審查基準仍為 b76f5e2。

## 分級方式

這裡不用 BUG 的 P0／P1，避免把產品偏好與資料損壞風險混在一起。

| 等級 | 意義 |
|---|---|
| A | 正式投入長篇製作／穩定發布前，應優先完成的基礎 |
| B | 明顯改善日常創作效率、理解與操作品質 |
| C | 隨專案規模或量測結果決定是否投入 |
| D | 有取捨，現階段不建議優先做 |

規模 S／M／L 是相對改動範圍，不是工期承諾。

## 一、UI、操作邏輯與作者工作流程

### U01｜共用工作區外殼與語言規則 — A／M

**現況：** v2、Explore、Classic 是不同根元件。實測同一專案在 v2 顯示 Galeng 與英文工具列，在 Explore 顯示 plane-engine 與中文工具列。已有跨殼儲存 gate、deep link 和部分共用面板，應延續這些成果。

**改善：** 共用專案名稱、場景導覽、Save 狀態、問題入口、設定、快捷鍵說明及 UI 語言；只在中央切換對話／探索的編輯表面。先抽共用元件與 session 服務，不必一次合併所有狀態。

**驗收：** 在兩種場景間往返，使用同一份語言設定、同一個專案狀態；保留各工作區的選取、捲動和面板配置。品牌文字可統一，內部格式／路徑名稱不必為改名而破壞相容性。

### U02｜依場景種類開啟正確工具 — A／M

**現況：** Script Library 已會把 Explore 列送往正確工作區。但在本次副本直接進入 `#dialogue`，起始場景 `study` 顯示黑色舞台與「Beat 0 of 0」，右側仍是對話欄位。這是入口理解問題，不能把空白畫面當成作者沒有內容。

**改善：** 統一場景導覽規則：依 `sceneKind` 開啟相應編輯器；無法直接編輯時顯示種類和明確入口。建立場景時提供「對話／探索」選項、用途提示及合理模板，顯示名稱與內部 ID 分開。

**驗收：** 同一個場景從 sidebar、腳本庫、搜尋結果、Call／Goto 連結打開，皆到達一致的編輯表面；初次進入混合專案即可找到起始場景。

### U03｜把「存檔狀態」做成作者理解的產品功能 — A／M

**現況：** 已有 dirty、projectDirty、儲存排隊、世代檢查、備份與離開防護；N1／N2 已處理特定競態。但使用者仍需要理解目前改了什麼，以及究竟寫到了哪一層。

**改善：** 統一顯示「有未存變更／儲存中／已儲存／失敗／外部版本衝突」，提供場景與專案的分項狀態。指出阻止存檔的欄位，讓作者直接跳過去；把存檔完成時間和版本作為可查看的細節。重載、關閉設定、跨場景與跨模式採一致政策。

**驗收：** 慢速儲存期間繼續修改，狀態不會提早變成已存；失敗有可重試入口且保留草稿；回復到已存版本時 dirty 語意一致。版本衝突需配合 E01 的 host 支援。

### U04｜依工作需要分配畫面空間 — B／M

**實測：** 1024px 寬的 v2 文件寬度為 1210px，Explore、Scripts、快捷鍵及 Settings 等頂部按鈕超出水平視窗；1440／1280px 樣本沒有同樣的水平超出。1280×720 對話畫面中，下方時間軸佔相當空間，即使場景只有三格；預覽中文字縮得很小。

**改善：** 工具列次要動作進 overflow 選單；面板可收合／調整大小，記住布局。提供寫稿、舞台、流程三種布局或少量可切換配置；預覽提供適合視窗／原尺寸／放大與平移。不要靠整體縮小文字解決空間。

**驗收：** 建議先以 1280×720 和 150% 縮放檢查必要操作可達性；若決定不支援 1024 寬，也應提供可操作的收合布局或清楚的最低視窗提示。遊戲輸出的 1920×1080 不等於作者瀏覽器必須同樣大小。

### U05｜完成鍵盤與對話框焦點管理 — A／S–M

**實測：** 新建場景視窗內按 Tab，焦點從輸入框、Cancel 走到 BODY，然後到背後的 New scene、Duplicate、Export 等工具列。視窗沒有 `aria-modal`。這不是只加一個 ARIA 屬性就能完成。

**改善：** 共用 Modal 負責初始焦點、Tab 循環、背景不可互動、Escape、關閉後返回觸發按鈕。補充 icon 按鈕的可存取名稱、label 與 input 關聯。v2 素材卡目前以 div 接 click／drag，應提供對等鍵盤套用方式。

**驗收：** 純鍵盤完成新建、選素材、修改、儲存；視窗開著時無法操作背後工具列。已有 focus-visible、部分 role 和 Problems 鍵盤導航應保留。

### U06｜降低 Explore 屬性面板的操作密度 — B／M

**現況：** 沒有選熱區時，右欄仍同時展示入場動作、空白點擊、轉場與各動作新增按鈕；矩陣、畫布、專案欄位又在其他位置。能力充足，但初學者要自行辨認作用範圍。

**改善：** 明確分成專案／房間／目前熱區／目前矩陣格；顯示選取摘要。把重複的新增動作按鈕收成一個「新增動作」選單，常用項可保留快捷操作；條件、轉場等進階設定預設收合並顯示摘要。

**驗收：** 作者能直接回答「正在改整個遊戲、這個房間，還是某個物件的某個動作」；切換選取不丟失草稿，也不產生意外 undo 步驟。

### U07｜讓矩陣符號與 fallback 規則直接可讀 — B／S–M

**現況：** 矩陣用 `·／●／▣` 表達內容狀態；Trace 已提供優先層級及「預計勝出」。覆蓋率文字也已說明不必填滿，這是正確方向。

**改善：** 矩陣旁放固定圖例，hover／鍵盤聚焦顯示動作摘要、是否附條件、會用哪個 fallback；大矩陣固定列頭／欄頭，提供未配置、有條件、物品互動等篩選。避免把填滿比例設成作者必須追逐的完成度。

**驗收：** 不打開完整 Inspector 也能分辨空格是刻意使用 fallback、明確自訂，還是需要作者處理。

### U08｜統一「繼承／清除／覆寫」的欄位語意 — B／M

**依據：** 對話預覽逐格累積背景、角色、音樂與 CG；空值、缺省值和顯式清除在不同欄位有不同含義。

**改善：** 對延續型欄位顯示「沿用上一格（來源 #…）／在此設定／在此停止或清除」，區分儲存值和最終生效值。用資產選擇器、單位和上下限取代作者猜路徑、猜毫秒。

**驗收：** 刪掉欄位內容時，作者知道是在取消覆寫還是停止顯示／播放；跳到中段也能看到狀態來源。具體欄位仍遵守各自 schema，不強行把所有 null 當成同一件事。

### U09｜為長篇對話提供高密度編輯方式 — B／M

**現況：** 有 beat 時間軸、搜尋、說話者、語音與腳本匯出；短場景容易看，長篇寫稿則需要較多橫向移動及逐格操作。

**改善：** 在現有 IR 上增加可選的表格／文字清單視圖；支援連續輸入、批次設說話者、插入多格、複製區段、選區替換與可靠的鍵盤操作。更改先預覽影響，作為一次可復原操作。

**取捨：** 不是新增另一份劇本真相，也不需要先做腳本雙向解析。先改善最常用的逐句編輯。

### U10｜素材使用與引用整理形成完整流程 — B／M–L

**現況：** 已有分組、搜尋、縮圖、試聽、引用資訊及素材根目錄。不要重造基本素材瀏覽器。

**改善：** 點選預覽與套用到格子的效果更明確，套用後顯示目標與可復原提示；缺失／格式不支援／未使用分開顯示。先做 relink 與「查看全部引用」，其後再做帶 dry-run 的安全重命名與路徑更新。匯入若加入，需定義複製進專案或外部引用的可搬移性。

**驗收：** 換一個音檔或改一個素材名稱，作者可以先看到受影響場景；任何批次改引用都能回復，不先加入一鍵清理未使用檔案。

### U11｜把問題面板變成修正流程 — B／M

**現況：** 已有分類、嚴重性、場景分組及點擊定位；Trace 也有條件限制說明。

**改善：** 每條問題提供「發生在哪裡／對遊戲有何影響／如何處理」，精確跳到欄位或矩陣格。明確區分未檢查、檢查中、資料讀取失敗和已檢查無問題。可合理忽略的提醒記錄原因與範圍，不永久吞掉全部同類提醒。

**驗收：** 調整資料後對應問題會更新；無法讀取某場景不會讓作者誤解成該場景沒有內容或沒有問題。

### U12｜試玩要表明採用哪個起始狀態 — A／M

**現況：** 已有「Play from here」與原生啟動；但中途進場除了場景／格數，還依賴變數、背包、呼叫堆疊及前面建立的舞台狀態。runtime 的 Explore CLI 跳轉也有明確限制。

**改善：** 分清楚「從遊戲起點／從目前場景的初始狀態／從測試快照」；保存可命名的測試情境。把未支援的跳轉說清楚。開發用變數監看與真正的執行 Trace 應顯示條件值和命中原因。

**驗收：** 同一測試情境可重複得到相同結果；作者不會把缺少前置物品造成的分支差異誤認成遊戲 BUG。開發工具預設不進玩家發行版。

### U13｜復原、重載和備份提供一致的信任感 — A／M

**現況：** 對話已有 80 步 scene 快照；Explore 有 100 步 doc 快照、command label 與 coalesceKey；v2 有本機草稿恢復。問題不是「沒有 undo」。

**改善：** 明確規定一次輸入、一次拖動、一次批次變更各算幾步；顯示「復原：移動熱區」等操作名稱。場景與專案設定的復原範圍一致可理解。備份以專案身份、文件身份、版本辨識，恢復前顯示時間與差異，採有上限的保留政策。

**驗收：** 一次拖動只需一次復原；資料復原不改掉目前工具；刪除、重載、換專案後不會把舊草稿當成另一份文件。這是進一步規範，不能把已修 N2 再列為未修。

### U14｜改善玩家閱讀與設定的表達 — B／M

**依據：** 已有文字速度、自動播放、音量、語言、效果、按鍵映射、backlog 等基礎。settings 把 SIMD 與玩家常用選項放在同一組設定模型。

**改善：** 玩家可直接理解的字級、文字速度、語音等待、效果開關優先；技術診斷選項放進進階頁。作者可預覽長句、標點、混合中英日文和不同文字尺度，並驗收存檔縮圖／場景標籤、返回閱讀位置及聲音反饋。

**限制：** 本次沒有實際操作 Windows 玩家 UI，因此是依設定／繪字程式提出的驗收方向，不是實測判定所有閱讀功能都不好。保留已有功能，先找可用性缺口。

## 二、內核、資料與執行架構

### E01｜把文件版本與持久化規則落到 host — A／L

**現況：** 前端同頁寫入排隊已改善，但不能代表不同分頁、不同程序和外部檔案修改都被序列化。host 的 project／scene 儲存及玩家 slot 寫入目前使用直接 `fs::write`。

**改善：** host 提供版本 token／ETag，寫入時原子地比較版本再更新；衝突回傳可理解的資料，由 UI 保留本地草稿、重讀及比較。用同目錄暫存與適當的替換方式改善單檔寫入可靠性，針對 Windows 語意與失敗情況驗證。多檔改名／引用更新另定批次交易或可恢復流程。

**取捨：** 不需要為此把專案改成資料庫，也不必上 CRDT。單檔原子替換不是多檔交易，前端 GET 後 PUT 也不等於原子版本檢查。

**驗收：** 兩分頁、外部修改、寫入失敗與程序中斷可得到可解釋結果；既有檔案或草稿有恢復途徑。先完成版本衝突與單檔持久化，再談多人即時協作。

### E02｜明確定義對話／探索共用的執行契約 — A／L

**依據：** `Runtime` 與 Explore `Engine` 各持有部分場景、變數、階段、音樂和跳轉邏輯；啟動模式也影響執行路徑。這增加跨模式功能演進時重複補規則的成本。

**改善：** 先寫可測試的行為規格：Enter／Advance／Choose／Call／Return／Goto 的前置條件、一次性副作用、暫停點和返回位置。共用狀態快照及事件介面，讓 view／audio／save 消費同一套明確資料；逐步抽出重疊邏輯。

**驗收：** 從對話或探索起步，進到同一段內容時執行相同的舞台、語音、變數及跳轉規則；Call 後剩餘動作如何處理有明確規格。先以案例鎖定語意，再調整結構，不為追求單一大 VM 而一次重寫。

### E03｜JS 預覽與 Rust 播放器使用共同的案例真值 — A／M

**現況：** 共用 schema 能證明資料形狀，不能證明多個執行器語意相同。JS `previewState` 與 Rust 的狀態推導仍是不同實作。

**改善：** 建立少量高價值 fixture：繼承／清除、分支、Call→Return、變數更新、語音與自動前進、存讀檔。每一步比對規範化的狀態／事件；畫面上區分編輯預覽能表達的內容與需要原生試玩的內容。

**驗收：** 新增欄位時同步列出 schema、editor、preview、runtime、save、packer 的支援狀態；同一 fixture 的可比較欄位一致。音訊時序／渲染等不能以單張靜態預覽證明的部分另外測。

### E04｜把存檔相容性當成正式產品契約 — A／M–L

**現況：** 已有 saveFormat 3、舊格式讀取、game ID／schema 檢查和頂層 beatId。不是從零開始。

**改善：** 定義專案資料版本、存檔格式版本、遊戲內容版本各自責任；跨模式穩定位置 ID、呼叫堆疊、物品、音樂、一次性副作用均有恢復規則。保留舊版 fixture，說明新增／刪除／重排內容後哪些存檔能繼續。

**驗收：** 更新後可恢復的存檔正確恢復；不能恢復時顯示原因與可選替代入口，不靜默跳錯位置。是否儲存進行中的動畫／音訊精確時間應由產品需求決定，不能無限擴大快照。

### E05｜拆開 UI、文件服務與執行副作用 — B／M–L

**依據：** `useEditorState.ts` 約 1351 行、ExploreWorkspace 約 1510 行、InspectorPanels 約 1229 行、player/window 約 2761 行。行數本身不是 BUG，但它們聚集了多種責任，影響改動可審查性。

**改善：** 以責任拆分：文件 session／保存協調、場景導覽、命令歷史、播放啟動；播放器拆成輸入路由、狀態轉移、畫面組裝及 I/O 邊界。先抽純函式與小介面，保持對外行為。

**驗收：** 改字體或匯出 UI 不需觸碰場景儲存核心；測試文件競態不需掛載整個大型介面。避免純粹把大檔拆成大量互相依賴的小檔。

### E06｜錯誤要保留原因及資料可信度 — A／M

**具體依據：** Script Library 在場景載入失敗時，會生成 `beats: []` 的替代 scene；這讓「讀取失敗」容易被當成「真的沒有內容」。host 多數 API 以文字錯誤回傳，前端較難一致處理。

**改善：** 用可辨識的錯誤種類和狀態：not found、validation、conflict、unsupported、I/O；同時保留文件位置與使用者可理解的說明。資料列表用未載入／失敗／已載入狀態，不能拿虛構的空內容當成功結果。記錄已有 diagnostics 時保留其路徑清理策略。

**驗收：** 模擬單一場景讀取失敗，列表可重試，匯出會說明不完整，不會默默漏掉內容。開發者有可追蹤原因，作者有可執行的下一步。

### E07｜以量測制定播放器整體資源預算 — B／M

**現況：** 圖片已有約 320 MiB LRU 預算，window 也有靜態圖層快取；字形以字元與大小做快取。不能聲稱播放器沒有快取或一律需要更高階渲染器。

**改善：** 量測常駐記憶體、圖片解碼瞬間峰值、framebuffer、字形／音訊／影片、長時間換場景的成長。先提供診斷數據，再決定字形快取上限、尺寸離散化、預載或解碼排程。

**驗收：** 在既定最低硬體有啟動、P95 frame time、換場景、聲音中斷與記憶體峰值的基準。2 GB 是整機規格，不能直接當成遊戲可全部使用的記憶體。此次沒有量測，不能斷言已超標。

### E08｜讓大型專案的載入與編輯成本可控 — C／M

**依據：** Script Library 逐個 await 讀取場景；兩套 undo 使用整份文件快照；預覽逐格累積狀態。這些在小專案合理，在大型資料上值得量測。

**改善順序：** 先用 100／1000 場景、長對話與大量熱區建立基準；再選擇有上限的並行讀取、增量目錄、快取與失效機制、長列表虛擬化。歷史先按操作分組及設記憶體預算，確定瓶頸後才改 patch-based undo。

**驗收：** 記錄讀取次數、初次與重開時間、輸入／拖曳延遲及 undo 記憶體；改善不帶來過時列表或丟失復原能力。不要未量測就全部換狀態管理框架。

### E09｜打包改成受控、可觀察的工作 — B／M

**依據：** packer 先把引用素材讀入 `Vec<(String, Vec<u8>)>` 再寫 zip；host 的 async pack handler 直接呼叫同步匯出流程。已有 strict 模式與素材引用掃描，應繼續使用。

**改善：** 分成驗證／逐檔讀寫／產出報告，降低總素材量造成的記憶體峰值；同步工作放到合適的 blocking worker，限制重複匯出，提供階段與錯誤。使用暫存輸出和成功後提交的策略，避免失敗時留下看似完成的成品。

**驗收：** 大素材包匯出時仍可得到 host 狀態回應；中斷／磁碟不足不把半成品標為成功。先做到可靠完整包，再評估增量包、可重現二進位與差分更新。作者端是現代 PC，勿把玩家的 2 GB 直接套作作者限制。

### E10｜強化 schema 演進的一致性，而非重複驗證 — B／M

**現況：** TS AJV 和 Rust 已使用共用 JSON schema，但 TS／Rust 型別及 UI／runtime 行為仍需同步。

**改善：** 每個新增欄位附語意、預設、清除方式、相容性、素材引用與存讀檔測試。能可靠生成的型別再評估生成；先以契約 fixture 揪出 drift。未知欄位的保留／拒絕策略要明確，避免不同寫入路徑各自猜測。

**驗收：** 一個欄位可以從輸入、編輯、儲存、打包到玩家完整往返；舊版本遇到新內容有明確結果。

### E11｜把文字排版品質納入內核驗收 — B／M

**依據：** 字體有 fallback、字形快取、wrap_lines 等功能；目前所讀換行邏輯主要逐字累計寬度。專案以中文和英文作者／玩家為主，也允許日文內容。

**改善：** 測試中文行首行尾標點、英文單字、組合字元、混合字體、缺字與長選項；視需求改善換行／分頁與輸入字串邊界。確認播放器和預覽採不同字體時的可見差異。

**驗收：** 一組多語文排版樣本在支援字體與尺寸下沒有截斷、看不見選項或不合理分頁。不因未宣布支援的書寫系統而先導入龐大排版引擎。

## 三、開發、測試、交付與文件

### Q01｜修復乾淨環境的依賴可重現性 — A／S

目前 `apps/editor/package.json` 宣告 `@playwright/test`、`@types/node`，但 `pnpm-lock.yaml` 的 editor importer 沒有這兩項；CI 使用 frozen lockfile。應同步 manifest／lock，固定可驗證的工具鏈，從乾淨 clone 驗收。已有 node_modules 的環境測試通過不能代替這項檢查。

### Q02｜把真實作者流程納入每次合併檢查 — A／M

一般 CI 目前跑 Rust／JS 測試，未包含 editor build 或 Playwright。push 觸發只列 master；直接推 work 是否執行檢查不能從「已 push」推定。Release 會經 `pack-author.bat` 建 editor，不能說整個發布流程都沒有 build。

建議 PR 必須通過乾淨安裝、型別／正式建置、單元測試、少量關鍵 E2E。涵蓋建立→編輯→保存→切模式→刪除／復原、慢網路、失敗重試和雙分頁衝突；新增本次焦點與窄視窗驗收。優先覆蓋使用者後果，不把測試數量當品質分數。

### Q03｜把 Windows 8.1／舊硬體承諾變成可證明結果 — A／M–L

README／SPEC 宣稱 Windows 8.1／10、Core 2 Duo、2 GB、DX9；`windows-latest` 不是該環境。編輯器用現代作者 PC 與播放器用舊 PC 的要求也要分開寫。

建立「目標／已實測」矩陣，記錄 OS、架構、CPU 指令集、SDL／影片／音訊依賴及建置工具鏈。發版前在對應實機或合適環境測啟動、存讀檔、素材、聲音、影片與 Unicode 路徑；硬體效能仍要實機。無法維持的目標應調整承諾，不以現代 CI 綠燈代替。

### Q04｜對發行成品做端到端 smoke test — A／M

已有作者 ZIP、checksum 和 release workflow。補上從壓縮包解壓、沒有 Rust／Node 的環境啟動、開作者專案、匯出遊戲、在獨立位置執行 player 的流程；覆蓋空白／中文路徑與失敗回報。驗收輸出成品，不能只驗收倉庫中的原始碼。

### Q05｜統一目前狀態、設計決策與歷史交接 — B／S–M

設計文件同時承載初期規劃、舊缺陷和後加的修正說明；只讀中段容易重報已修問題。每份文件加上適用 commit／版本與目前結論，歷史部分保留日期。建立一份功能支援表和待辦索引；Call continuation、存檔兼容、資料所有權等語意用短決策文件記錄。

驗收：新接手者能知道什麼已做、什麼仍待定，並能找到對應測試；不要靠無限增長的 HANDOFF 取代現況文件。

### Q06｜讓本機 host 的邊界符合其用途 — A／M

實際程式預設 bind loopback，但 CORS 允許 Any，API 包含寫專案、匯出與啟動。宜明確允許的 origin／host，必要時使用本機 session token，維持路徑與寫入範圍驗證；測試合法作者 UI 仍可工作。這是依具體配置提出的加固項，本次沒有進行完整安全滲透或宣稱已證實跨站利用。

### Q07｜逐步減少三套 UI 的維護負擔 — B／M

先列出 Classic 相對 v2 的不可替代能力與使用情況；補齊阻礙後，停止向 Classic 加新功能，保留過渡期和設定遷移。不要直接刪除舊殼，也不要長期要求每一個功能永遠實作三次。共用 session 服務可先減少 N1／N2 這類修正需要多處同步的成本。

## 四、與先前 BUG 審查的關係

- N1／N2 已在本次基準 commit 修正。此處建議的是把修正背後的資料生命週期規則持續收斂成共用機制。
- 舊審查記錄的跨模式執行、Explore 恢復位置、音樂恢復、動作佇列、跨分頁寫入等問題，仍應按其修復／複驗清單追蹤；本次沒有把那些舊重現全部重新執行，也不新增它們的嚴重性判定。
- 美化與便利功能不能取代未完成的正確性修復。最合理的安排是修復時同時補行為 fixture，避免為了改善架構長期拖延明確 BUG。

## 六、現階段值得商榷／不建議優先做的事

1. **全面換 Electron／Tauri 或把播放器改 Web。** 與目前 native／低配目標不一致，不能直接解決文件生命週期與執行語意問題。
2. **增加 3D、Live2D、大型插件系統或通用腳本 VM。** 明顯擴大維護範圍；目前更需要可靠完成既有 AVG＋探索作品。
3. **先做完整腳本雙向匯入。** README 明確採 JSON 為真相、腳本供校對；雙向編輯需先解決 ID、排序、格式損失與衝突。高密度寫稿 UI 的投入更可控。
4. **把所有 state／undo 一次換成新框架。** 既有命令匯流排和快照能工作；先量測、定契約和拆責任。
5. **用資料庫、CRDT 解決所有存檔問題。** 目前先完成原子版本檢查、單檔可靠寫入和明確衝突處理，收益更直接。
6. **沒有數據先做多執行緒、SIMD 或全新 renderer。** 已有圖層與圖片快取、SIMD 設定；優先找真正熱點及最低硬體瓶頸。
7. **把所有畫面改成同一種編輯形式。** 共用導覽、規則和視覺語言即可；對話格與熱區矩陣本來就服務不同任務。
8. **用全面自動儲存掩蓋資料競態。** 自動儲存有價值，但須先有可靠版本與衝突模型，也要明確區分草稿備份和正式落盤。
9. **一鍵刪除未引用素材。** 在動態引用／完整掃描可靠性尚未證明前，先做可審查清單、隔離及恢復，避免整理功能造成資產損失。
